PayPal Invoice Copilot

How it works

One request, "Invoice Acme Corp $500 for logo design, due in 14 days", traced through the code from chat to confirmed send.

Big picture

Chat text goes to /api/chat, where the demo agent or the LLM calls the invoice tools. Tools that write to a client (send, remind, cancel) only record a pending action. A click on the confirmation card posts to /api/confirm, and executePendingAction runs it against the PayPal Agent Toolkit or the in-memory store. The desk then refreshes from /api/invoices.

The dashed box is the default: with no keys every write lands in the in-memory store. The PayPal path is taken only when both PayPal keys are set, the server is bound to loopback (scripts/serve.sh), it is not a hosted deploy, and the cached Invoicing probe (probePayPalInvoicing) succeeds. Every request first passes guardRequest.

Source: src/components/ChatPanel.tsx (send, handleConfirm), src/app/api/chat/route.ts, src/app/api/confirm/route.ts, src/lib/paypal-tools.ts (getInvoiceTools, executePendingAction)

Step by step

One request, Invoice Acme Corp $500 for logo design, due in 14 days, from chat to confirmed send. The diagram walks through the steps below on its own.

  1. Send — src/components/ChatPanel.tsx posts the last 30 messages as JSON. src/lib/access.ts:guardRequest rejects non-JSON (415), cross-origin requests (403) and, while live credentials are active, non-loopback callers (403); src/lib/chat-input.ts:parseChatBody accepts only user/assistant text with size limits. ensureSession sets the HttpOnly ic_sid cookie.
  2. Pick the agent — src/app/api/chat/route.ts:POST runs runDemoAgent unless isLlmConfigured() (an LLM key, no DEMO_MODE/FORCE_DEMO_AGENT, a loopback bind, a valid base URL); otherwise getInvoiceTools({owner}) + generateText with maxSteps: 6.
  3. Draft — demo path: src/lib/demo-agent.ts:runDemoAgent extracts amount, business, service and due days and calls mock.createInvoice (row source local-mock). LLM path with a passing probe: create_invoice creates a PayPal sandbox draft and keeps a desk row via mock.upsertLiveInvoice (source paypal-sandbox); on a PayPal error it returns the error and creates nothing.
  4. Propose, do not act — send_invoice, send_invoice_reminder and cancel_sent_invoice call proposeAction → src/lib/pending.ts:createPendingAction (owner = session, 15-minute TTL) and return needs_confirmation. The model has no tool that can confirm. If it drafted but did not propose a send, the route proposes one (auto-queue-send); it never executes.
  5. Show the card — the reply carries pendingAction and its summary says where it will run ("local mock desk" or "PayPal sandbox"); ChatPanel renders ConfirmCard.
  6. Confirm — /api/confirm validates {pending_action_id, confirmed} and reads the owner from the cookie. confirmed:false cancels the action (cancelled_by_user).
  7. Execute once — src/lib/paypal-tools.ts:executePendingAction claims the action (other session 403, expired 410, already done 409). Local rows change status in memory; PayPal rows go to the toolkit after a cached probe. Failure before dispatch returns it to pending (up to 3 tries); a dispatched call with an unknown result becomes outcome_unknown and is never retried.
  8. Refresh — ChatPanel prints the result with its source, keeps the card only if the action is retryable, and AppShell reloads /api/health and /api/invoices.

Source: files named in each step; checked by running the zero-key build on 2026-11-07 (draft → Confirm → SENT; a second Confirm returned already_executed; no cookie → 403; cross-origin → 403; form post → 415).

Failure paths

  • Bad request: non-JSON POST → 415; cross-origin → 403; invalid JSON or schema → 400; non-loopback caller while live credentials are active → 403 live_mode_local_only.
  • LLM call throws → /api/chat returns 502 with a sanitized category (publicLlmError): no key, URL or raw provider body. A model that calls an unknown tool, such as confirm_pending_action, fails the same way and nothing executes.
  • PayPal not usable (credentials missing, rejected config, hosted deploy, non-loopback bind, probe failing): the tools stay on the local mock desk and the badge and /api/health say why.
  • Live create or list fails → the error is returned; no mock rows are substituted. /api/invoices answers 502 with items: [].
  • Confirm: other session 403; unknown 404; expired 410; already executed, in progress, failed, cancelled or outcome_unknown 409; invalid invoice state 409 (terminal failed); PayPal unavailable before dispatch 503 (back to pending, retryable up to 3 times); PayPal 4xx 502 paypal_rejected; dispatched with an unknown result 502 outcome_unknown (never retried; check the PayPal dashboard); unexpected 500.
