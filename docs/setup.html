PayPal Invoice Copilot

Setup

From a fresh clone to a running app: the zero-key demo needs only Node.js; live mode adds PayPal sandbox and LLM credentials.

Prerequisites

  • Node.js with npm. Version not pinned for local runs: package.json has no engines field. The only pin is NODE_VERSION: "20" in render.yaml, for the Render deploy. Node 20 is the safe choice.
  • bash. The dev, build and start scripts call bash scripts/with-swc-fallback.sh / bash scripts/build.sh.
  • Accounts: none for the default mode. The zero-key demo uses the built-in demo agent and the in-memory mock store.
  • Optional, for live mode: a PayPal Developer account with a sandbox REST app that has Invoicing enabled (Developer Dashboard → Apps → Features), and a key for one OpenAI-compatible LLM provider (Groq, OpenRouter, Google AI Studio or OpenAI, as listed in .env.example).

Source: package.json, render.yaml, .env.example, README.md

Install

git clone https://github.com/nnquangit/paypal-invoice-copilot.git
cd paypal-invoice-copilot
npm ci

No config file is needed for the demo. For live mode, copy the example file and fill it in (next section):

cp .env.example .env.local

Source: README.md (Quick start, Live PayPal sandbox + LLM)

Run

npm run dev      # bash scripts/serve.sh dev   → next dev -H 127.0.0.1 → http://localhost:3000
npm run build    # bash scripts/build.sh → next build
npm start        # bash scripts/serve.sh start → next start -H 127.0.0.1

scripts/serve.sh chooses the bind address and refuses an extra -H/--hostname. It exports IC_BIND_HOST, and src/lib/config.ts honours PayPal and LLM credentials only when that is a loopback address. A server started another way (plain next start, a public bind) runs as the zero-key demo.

Port 3000 is the Next.js default; the README links http://localhost:3000. Restart the dev server after editing .env.local.

Force the zero-key demo in a checkout that already has keys:

DEMO_MODE=true FORCE_DEMO_AGENT=true npm run dev

Live mode is local-only. With PayPal or LLM credentials active, every API route answers only loopback requests (localhost, 127.0.0.1, [::1]); anything else gets 403 live_mode_local_only. That header check is defence in depth, because headers can be forged. The real control is the 127.0.0.1 bind from npm run dev / npm start.

Deploy (demo only). Vercel (vercel.json: framework, region iad1) and Render (render.yaml: one free instance, npm ci && npm run build, then npm run start with PUBLIC_DEMO=true and DEMO_MODE=true, which binds 0.0.0.0) run the zero-key demo. serve.sh refuses PUBLIC_DEMO=true without DEMO_MODE=true. The app ignores PayPal and LLM credentials there, because it has no authentication and keeps state in one process's memory.

Read these docs. The pages in docs/ are static HTML: open docs/index.html directly, or serve the folder with python3 -m http.server 4590 --bind 127.0.0.1 --directory docs and open http://127.0.0.1:4590/.

Verify

  1. Open http://localhost:3000. The header badges read Demo mode, PayPal: local mock (no PayPal calls) and LLM: built-in demo agent with no keys set (src/components/ModeBadge.tsx). The desk shows two seeded invoices, INV-1001 (SENT, USD 850.00) and INV-1000 (PAID, USD 1200.00).
  2. Ask the health route: 
    curl -s http://localhost:3000/api/health
    Expect "ok": true and a mode object. In live mode paypalInvoicingOk: true means the Invoicing probe passed.
  3. Send Invoice Acme Corp $500 for logo design, due in 14 days; a local mock draft and a Human confirmation required card appear. Confirm, and the desk shows the invoice as SENT (local desk only, no email is sent).

Source: src/app/api/health/route.ts, src/lib/mock-store.ts (seed), src/components/ConfirmCard.tsx

Troubleshooting

SymptomCause (from code)Fix
Badge says "PayPal: sandbox · invoicing unavailable"Credentials are set, but the probe fails (for example the REST app lacks the Invoicing feature). The agent then uses the local mock tools, and every result says source: "local-mock".Enable Invoicing under Apps & Credentials → Features. The probe result is cached for 15 s on failure, 60 s on success.
Badge shows "PAYPAL_ENVIRONMENT=… rejected"Sandbox-only buildUse sandbox or leave it empty
API returns 403 live_mode_local_onlyLive credentials are active and the request did not come from loopbackOpen the app on http://localhost:3000 on the same machine, or use DEMO_MODE=true
Badge shows "PayPal credentials ignored: the server is not bound to loopback"The server was not started with npm run dev / npm start, or PUBLIC_DEMO=true was setStart with npm run dev
Confirm says "… outcome_unknown"The request reached (or may have reached) PayPal, but the call failed ambiguously (network error or 5xx). The action is never retried.Check the invoice in the PayPal sandbox dashboard, then propose a new action only if it did not happen
Confirm says "Not executed (HTTP 403 · forbidden)"The pending action belongs to another browser session (cookie ic_sid)Ask again in this browser
Chat replies LLM error: … (HTTP 502)The LLM call failed. Only a category and HTTP status are shown; the redacted detail is in the server log.Check LLM_* (default model openai/gpt-oss-20b)
Live send fails with "User is not associated with paypal"An invoicer email that is not the sandbox merchant's (comment in getInvoiceTools)Leave MERCHANT_EMAIL_USE_ON_INVOICE unset, or set MERCHANT_EMAIL to the sandbox merchant email
"Native SWC unavailable … using WASM fallback"The native SWC binary fails to load on some Linux hostsNothing to do: the script moves it aside and uses @next/swc-wasm-nodejs (it may run npm install --no-save once)
"I didn't catch that."The demo agent only knows fixed phrasings (regular expressions)Use the suggestion chips or the examples in the reply
Invoices disappear after a restart or between serverless instances; confirm returns 404 not_foundThe store and pending actions live in one process's memory (globalThis)Expected for the prototype. Run a single process; restart to reseed the demo state.
