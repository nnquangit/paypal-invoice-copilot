PayPal Invoice Copilot

Security

A hackathon prototype. Send, remind and cancel follow an intended two-step flow (propose, then confirm). That flow is a UX safeguard, not an enforced human-only security boundary: the LLM can also confirm, and no route requires authentication. Several review findings are still open. Every statement below points to code.

Assets & trust boundaries

  • PayPal REST credentials (PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET): read only on the server (src/lib/paypal-tools.ts). Honoured only for PayPal sandbox, only when no hosted platform is detected, and only for loopback requests (see below).
  • LLM key (LLM_API_KEY): server only (src/lib/llm.ts). Each /api/chat call spends quota.
  • Invoice data: recipient emails, names and amounts in the in-memory store and, in live mode, in the PayPal account.
  • Outbound effects: emails PayPal sends to recipients on send / remind, and cancellation of real invoices.

Untrusted input enters at the four API routes: the messages body of POST /api/chat (validated by src/lib/chat-input.ts, then passed to the LLM or the regex agent), the POST /api/confirm body (zod-validated), and query parameters of GET /api/invoices (clamped). A second untrusted source is model and tool output, which ChatPanel renders as React elements through src/lib/markdown-lite.ts (no HTML strings).

There is no user authentication. The app is meant for a single person on their own machine. The controls below are a local-only restriction plus per-browser ownership, not identity.

Secrets handling

  • Supplied as environment variables in .env.local for local runs (README). Hosted deploys (render.yaml, Vercel) are demo-only: the app ignores PayPal and LLM credentials when RENDER or VERCEL is set.
  • Only server code reads them. No client component reads process.env, and there are no NEXT_PUBLIC_ variables.
  • /api/health returns booleans, sandbox or mock, the LLM provider hostname (only when the LLM is active), the model name, and configuration warnings. It does not return keys. A malformed LLM_BASE_URL no longer crashes it.
  • Must never appear in the repo, logs or docs. These pages list variable names only. Server errors are logged through logServerError, which redacts and truncates. Redaction is pattern-based, so treat logs as sensitive anyway.

Known gaps

The earlier review items (HITL bypass, sandbox guard, mock/fallback honesty, confirm errors, XSS and role injection, QR truth, probe cache, totals) were fixed in the code-fix pass of 2026-11-07, and offline regression tests were added under tests/. Whether those tests pass was not confirmed in that pass: dependency installation (npm ci) was not permitted in that session, so npm test, tsc and npm run build did not run. See .agent-reports/code-fixes-result.md. What remains:

  1. No authentication. Live mode relies on the 127.0.0.1 bind (scripts/serve.sh + IC_BIND_HOST). Anyone with a shell on the machine, or a user who deliberately overrides the bind, is trusted.
  2. Single-process memory. Invoices and pending actions live in one Node process. They are lost on restart and not shared between instances. "At most one dispatch per action" holds per process only. The app therefore refuses credentials on Vercel/Render, and render.yaml pins one demo instance. In demo mode on serverless, a confirm can still hit another instance and get 404 "not found".
  3. Unknown outcome. A dispatched PayPal call that fails ambiguously becomes outcome_unknown and is not retried. The action may or may not have happened, and only the PayPal dashboard can tell. Reconciliation is manual.
  4. QR is a placeholder in every mode: it is clearly labelled and not scannable, and PayPal's QR API is not called.
  5. Summary totals add amounts across currencies, and the desk shows a $ prefix. They are correct only for single-currency desks.
  6. Desk separation: with PayPal sandbox active and FORCE_DEMO_AGENT=true, the demo agent writes local-mock rows that the PayPal-sourced desk list does not show.
